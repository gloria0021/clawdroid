# Research: サイドパネルの看板をバーチャルオフィスにする

**Created**: 2026-11-28
**Spec**: [spec.md](./spec.md)

マスターの依頼（2026-11-28）: 「サイドパネルの上部（エージェントの顔）を、画像のようなエージェントの働きを可視化するバーチャルオフィス空間にできないか。まず技術的に可能か、そういう OSS があるか探して」

## 結論

- **技術的には可能**。データ・描画・素材のどれにも、実現を止める問題は見つからなかった
- **似た OSS は多い**（2026 年 3 月から急増。OpenClaw 向けだけで 8 件以上）。ただし**すべて Web（ブラウザ・VS Code・Electron）用**。Android のアプリの部品として使えるものは無い
- **OSS は埋め込まず、Compose の Canvas で描くのを推す**。OSS からは「状態 → 居場所・動き」の対応の考え方と、CC0 の素材を借りる
- **ルールとの衝突が 2 つある**（AGENTS.md 2.8 の「ループし続ける演出の禁止」「読んでいる最中は動かさない」）。入れるなら `docs/design/screens.md` に例外を書く必要がある（spec の FR-024・025）
- 追加の指示（2026-11-28）への答え: ベッドは置ける（Kenney の Furniture Kit にベッドが 3 種、CC0）。キャラクターを選べるようにするのも、家具・部屋をいじれるようにするのも作れる（R7・R8）

## R1. 見せるための情報は Gateway から取れるか

| 見せたいもの | 取り方 | 状態 |
|---|---|---|
| どのセッションが動いているか | `sessions.list` / `sessions.changed` の `running`（`hasActiveRun`） | **取れる**。アプリはすでに受けている（`SessionSummary.running`。サイドパネルの実行中の印） |
| 終わって未読か | 同じく `unread` | **取れる**（未読の点） |
| 最後に動いた時刻 | `updatedAt` | **取れる** |
| どのエージェントのセッションか・名前・顔 | `agentId`・`agents.list` | **取れる** |
| 今なにをしているか（読む・書く・コマンド・検索） | `agent` イベントのツールの流れ、または `session.tool` | **一部確かめる必要あり**。`session.tool` は購読した 1 つのセッションだけに届く（`sessions.messages.subscribe`）。`agent` イベントはアプリが `session-scoped-events` を名乗っていないので、ほかのセッションの分も届いている可能性が高い（`ChatRepository` が key で弾いている）。実機の Gateway で、開いていないセッションのツールの流れが届くかを確かめる（plan で） |
| 承認を待っているか | `session.approval`（購読したセッションだけ・権限が要る） | 全部のセッション分を常に取る手段は**未確認**。v1 では使わない |
| 何をしていたかの一言 | `sessions.activitySummary.ensure`（モデルを使って要約を作る） | 取れるが**費用がかかる**。v1 では使わない |

根拠: `reference/openclaw/docs/gateway/protocol/rpc-session-control.md`・`rpc-bootstrap-and-events.md`（v2026.11.6 同梱）、`core/data/Models.kt`・`ChatRepository.kt`・`SessionsRepository.kt`。

**結論**: 「動いている・終わって未読・しばらく静か」の 3 つは、今アプリが持っているデータだけで出せる。新しい通信は要らない。「何をしているか」で動きを変えるのは、確かめてから足す（P3）。

## R2. 描き方の選択肢

| 案 | 中身 | 良い点 | 問題 | 判定 |
|---|---|---|---|---|
| **A. Compose の Canvas に 2D の絵を並べる** | 斜め上から見た部屋の絵（1 枚）＋家具・人の小さな絵（スプライト）を `drawImage` で重ねる。人の動きは数コマの切り替えと移動 | 依存を足さない（憲章 VI）。今の看板と同じ `graphicsLayer` での浮き上がり・フェード・Haze の透かす元がそのまま使える。描くのは見えているあいだだけにできる。軽い | 部屋・家具・人の絵を用意する手間。歩く経路などのロジックは自前 | **推す** |
| B. WebView に OSS を埋め込む | pixel-claw などの Web 版をアプリの中で表示 | 試すまでは速い | WebView は Haze で透かせない（今の看板は閉じるボタンの下で透けている）。開くたびの起動が重く、サイドパネルを引き出す動きと重なる（憲章 I）。Gateway のトークンを WebView の中の JavaScript に渡すことになる（憲章 IV）。見た目をアプリの色・言語・文字サイズに合わせられない | 不採用 |
| C. 3D（Filament / SceneView）で画像のようなボクセルの部屋 | glTF の部屋と人を 3D で描く | 画像に最も近い。角度を変えられる | GL の面はサイドパネルの動き（下から浮き上がる・フェード）と Haze に馴染まない。APK が数 MB〜10 MB 増える。電池。180dp の帯では 3D の良さが出にくい | 不採用（見た目は 3D の絵を前もって 2D に描き出して A で使えば近づけられる） |
| D. ゲームエンジン（KorGE・libGDX） | エンジンの画面を埋め込む | 歩く・当たり判定などが揃う | 帯 1 つのために大きすぎる。B・C と同じく別の描画面になる | 不採用 |

**画像（マスターの添付）の見た目について**: 斜め上から見たボクセル（積み木）風の部屋。A でも、部屋と家具は「3D で作って斜め上から描き出した 1 枚の絵」にすれば同じ見た目になる（Kenney の Furniture Kit は、この描き出し済みの絵が付いている）。動くのは人だけなので、人を 2D の小さな絵で重ねれば十分。

- 1 セッション = 1 人

## R5. 置き場所の大きさ

- 今の看板は、ステータスバーの下から 180dp（`Dimens.agentHeroHeight`）× 画面の幅（スマホで約 410dp）
- 斜め見下ろしの部屋なら、この帯に 6〜12 席は無理なく置ける。人 1 人は 24〜32dp ほど
- マスターの画像のように 30 人を出すと、名前の札が読めない。**人数の上限**と、**名前の札を常に出さない**（長押ししたときだけ）ことが要る（spec の FR-007・FR-016）
- 余白を出さない（マスター指定）には、部屋を枠より大きく作り、枠の縦横の比に合わせて映す範囲を切り出す。今の看板の画像と同じ「枠いっぱいに敷く」扱い
- デスク 8 ＋ ベッド 8 を 180dp に収めると窮屈になりうる。帯を高くするかは試作で決める（R10）

## R6. 動き・電池・既存のルール

- 動かすのは**サイドパネルが見えているあいだだけ**。閉じたら描くのを止める（今の看板の浮き上がりと同じく、描画の中で値を読む）
- 端末の「アニメーションを削除」では止める（アメーバと同じ扱い）
- 1 秒に数コマの切り替えで足りる（ドット絵の歩き・タイピング・寝息）。毎フレーム描くのは移動のあいだだけ
- **ルールとの衝突**:
  - AGENTS.md 2.8「ループし続ける演出」は、読み込み表示とアメーバだけが例外 → オフィスを例外に足す必要がある
  - AGENTS.md 2.8「読んでいる最中は動かさない」→ サイドパネルの履歴を読んでいるあいだも上で人が動く。動きを小さく・ゆっくりにするか、スクロール中は止めるか
  - AGENTS.md 2.1「装飾は内容を読む・操作するのを助けるときだけ」→ 状態（動いている・終わった）を表すときだけ動かし、意味のない歩き回り（ランダムな散歩）は入れない、とすれば筋が通る
  - 絵の色はテーマの色（`colorScheme`）ではない（絵として持つ）。今の看板のエージェントの顔の画像と同じ扱い（画像は色の直書きに当たらない）
- 憲章 VII（持ち歩くための道具）との関係: 「状態を確かめる」に当たる。今のサイドパネルでは、動いているセッションは履歴の行の小さな印でしか分からず、エージェントをまたいだ全体は見えない

## R7. 家具・部屋をいじれるか

**作れる**。Pixel Agents（MIT）に配置の編集の画面があり、作りが参考になる:
- 床をマス目に区切る。家具ごとに「占めるマスの大きさ（例 2×2）」「向きごとの絵」「壁に掛けられるか・机の上に置けるか」を持つ（Pixel Agents の `manifest.json`）
- 置く・動かす・回す・片付けは、マス目の上の当たり判定だけで済む
- 配置は JSON 1 つで持てる（端末に保存）

手間の大きい所:
- 家具の絵を、回せる向きの数だけ用意する（Kenney の描き出しは 4 方向付きなので、Kenney なら揃う）
- 斜め見下ろしでは、手前の家具が奥の人を隠す。描く順（奥から手前）を毎回決める必要がある（人がデスクとベッドのあいだを歩くときに入れ替わる）
- スマホの小さな画面での編集の操作（つまむ・動かす・回す）
- 家具を動かすと、デスクとベッドの割り当て・歩く経路が変わる

**判定**: 既定の部屋 1 つ（US1〜3）を先に出し、編集（US5）は後から足せる作りにしておく（配置を最初からデータで持ち、絵にべた描きしない）。

## R8. キャラクターを選べるか

**作れる**。2 つのやり方がある:

| やり方 | 中身 | 良い点 | 手間 |
|---|---|---|---|
| 部品の組み合わせ | 体・髪・服を別々の絵で持ち、重ねて描く（Pixel Agents・MetroCity の作り） | 組み合わせが多い。色だけ変える（髪の色など）こともできる | 部品ごとに、向き × 動きのコマを揃える。斜め見下ろしでは重ね順が向きで変わる |
| 出来上がりの一覧 | 完成した見た目を 8〜16 種類用意し、その中から選ぶ | 作るのも選ぶのも簡単 | 種類が限られる |

- ボクセル風（spec Q3 = A）なら、3D で作った人を描き出すので、どちらでも作れる。部品の組み合わせは、3D の段階で着せ替えて描き出す
- 選んだ見た目は端末に保存する。Gateway のエージェントには、顔の画像（`avatarUrl`）はあるが、キャラクターの項目は無い

**判定**: 出来上がりの一覧から始める（8 種類ほど）。選ばなければエージェントの id から決める。

## R9. キャラクターの絵のコマ数（目安）

Q1 = A（1 人 = 1 エージェント）・Q3 = A（ボクセル風）の場合:

| 動き | 向き | コマ |
|---|---|---|
| 歩く | 斜めの 4 方向（左右は反転で 2 方向に減らせる） | 4 |
| 座って作業（タイピング） | デスクの向き 1〜2 | 2〜4 |
| 寝る（ベッドで横になる・寝息） | 1 | 2 |
| 立ち止まる | 4（反転で 2） | 1 |

1 種類あたり 20〜30 コマ。8 種類で 200 コマ前後。1 コマ 32×48 px ほどなら、全部で数百 KB に収まる（spec SC-006）。

## R10. 試作（spike）で確かめること

plan に入る前に、使い捨ての試作で次を確かめる:

1. Kenney の絵を並べた部屋 1 枚（看板の枠いっぱい・余白なし）＋ 人 3 人（デスク・ベッド）を Canvas で描き、サイドパネルの引き出しの動きと一緒に 120Hz で滑らかに動くか（「アニメーター再生時間スケール」5x でも）
2. 開いていないセッションのツールの流れ（`agent` イベント）が届くか（実機の Gateway で）
3. 180dp の帯で何人まで見分けられるか（スマホ・文字 200%）。デスク 8・ベッド 8 が入るか、帯を高くする必要があるか
4. ボクセル風の人を描き出す手順（3D の人 → 斜めの向きのコマ）が回るか
